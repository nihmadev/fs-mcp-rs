Быстрый и гибко настраиваемый файловый сервер для Model Context Protocol (MCP), написанный на Rust.

`fs-mcp-rs` предоставляет MCP-клиенту компактный набор инструментов для работы с файловой системой, сохраняя доступ строго внутри каталогов, выбранных оператором. У сервера нет неявного корня файловой системы, встроенного персонального пути или режима записи по умолчанию. Сервер запускается только с явно указанным конфигурационным файлом.

## Почему один crate?

Публичная поставка состоит из одного crate и одного исполняемого файла с именем `fs-mcp-rs`. Компоненты протокола, политик, файловой системы, поиска и настроек остаются отдельными модулями Rust внутри crate. Благодаря этому установка остается простой:

```console
cargo install fs-mcp-rs
```

Пользователю не нужно устанавливать или разбираться в графе внутренних crate. Средство запуска бенчмарков остается участником workspace только для разработки и не входит в пакет crates.io.

## Возможности

- MCP поверх JSON-RPC HTTP POST.
- Явный список одного или нескольких разрешенных корней файловой системы.
- Режим «только чтение» для безопасных развертываний.
- Опциональные операции записи, перемещения, редактирования, создания каталогов и удаления.
- Ограничения на чтение, запись, число результатов поиска и параллелизм.
- Литеральный поиск и поиск по регулярным выражениям.
- Поддержка `.gitignore` и настраиваемая обработка скрытых файлов.
- Переход по символическим ссылкам по умолчанию запрещен.
- Атомарная замена файлов и хеши BLAKE3.
- Опциональное выполнение произвольных команд терминала с ограничениями времени и объема вывода.
- Постоянные сессии терминала с курсорами инкрементального вывода, long polling, stdin, завершением дерева процессов, временем хранения и ограниченными буферами.
- Без телеметрии и автоматического обнаружения сети.

## Требования

- Rust 1.85 или новее для сборки из исходного кода.
- MCP-клиент с поддержкой подключения к Streamable HTTP/JSON-RPC endpoint.
- Конфигурационный файл, созданный и проверенный человеком, запускающим сервер.

## Установка

### Из crates.io

```console
cargo install fs-mcp-rs
fs-mcp-rs --version
```

### Из исходного кода

```console
git clone https://github.com/nihmadev/fs-mcp-rs.git
cd fs-mcp-rs
cargo build --release
```

Исполняемый файл появится в `target/release/fs-mcp-rs` на Unix-подобных системах или в `target\release\fs-mcp-rs.exe` на Windows.

## Создание конфигурации

Скопируйте `configs/example.toml` в подходящее место и отредактируйте его. У сервера намеренно нет пути конфигурации по умолчанию:

```console
cp configs/example.toml fs-mcp-rs.toml
```

Windows PowerShell:

```powershell
Copy-Item configs\example.toml fs-mcp-rs.toml
```

Минимальная конфигурация только для чтения:

```toml
[server]
host = "127.0.0.1"
port = 8000
max_concurrency = 32
max_io_concurrency = 16

[filesystem]
roots = ["/home/alice/projects"]
read_only = true
max_read_bytes = 8388608
max_write_bytes = 8388608
follow_links = false

[search]
max_results = 1000
max_concurrency = 4
worker_threads = 4
regex_cache_capacity = 64
include_hidden = false
respect_gitignore = true

# ВНИМАНИЕ: разрешает произвольные команды с правами процесса сервера.
[terminal]
enabled = true
max_concurrency = 2
default_timeout_ms = 30000
max_timeout_ms = 300000
max_output_bytes = 4194304
```

Для корней Windows используйте экранированные обратные или обычные косые черты:

```toml
roots = ["C:\\Users\\Alice\\Projects", "D:/Shared/Documentation"]
```

Относительные корни разрешаются относительно каталога с конфигурационным файлом, а не относительно произвольного рабочего каталога процесса.

### Справочник по конфигурации

#### `[server]`

- `host`: IP-адрес для привязки. Оставьте `127.0.0.1`, если удаленным клиентам действительно не нужен доступ.
- `port`: TCP-порт для `/health` и `/mcp`.
- `max_concurrency`: максимальное число одновременно обрабатываемых MCP-запросов.
- `max_io_concurrency`: максимальное число одновременных файловых операций, не относящихся к поиску.

#### `[filesystem]`

- `roots`: непустой список разрешенных каталогов. Каждый запрошенный путь должен разрешаться внутри одного из них.
- `read_only`: при `true` все изменяющие инструменты отклоняются.
- `max_read_bytes`: максимальный размер ответа `read_file`.
- `max_write_bytes`: максимальный размер содержимого для `write_file` или результата `edit_text`.
- `follow_links`: разрешает переход по путям с символическими ссылками. Оставьте `false`, если последствия не были тщательно проверены.

#### `[search]`

- `max_results`: максимальное число совпадений одного поиска.
- `max_concurrency`: максимальное число одновременных поисковых задач.
- `worker_threads`: число потоков обхода файловой системы для каждого поиска.
- `regex_cache_capacity`: число скомпилированных поисковых шаблонов в памяти; `0` отключает кеш.
- `include_hidden`: включает скрытые файлы и каталоги.
- `respect_gitignore`: применяет правила Git ignore при обходе каталогов.

#### `[terminal]`

- `enabled`: включает выполнение команд. Если отключено, `run_command` возвращает ошибку инструмента.
- `max_concurrency`: максимальное число одновременно выполняемых команд.
- `default_timeout_ms`: тайм-аут, если вызов не указывает свой.
- `max_timeout_ms`: максимальный тайм-аут, который может запросить вызов.
- `max_output_bytes`: максимальный суммарный объем stdout/stderr, сохраняемый для одной сессии. Старые данные вытесняются и помечаются как отброшенные или усеченные.
- `max_read_bytes`: максимальный объем вывода одного вызова `terminal_read`.
- `max_wait_ms`: максимальная длительность long polling одного вызова `terminal_read`.
- `session_retention_ms`: время хранения завершенных сессий и их вывода до автоматической очистки.

`run_command` выполняет произвольные команды через `cmd.exe` в Windows и `/bin/sh` в GNU/Linux и macOS. Инструмент объявлен с destructive и open-world аннотациями MCP, чтобы совместимые клиенты могли показывать предупреждение. Включение дает командам все права учетной записи ОС, под которой работает сервер; корни файловой системы и режим только для чтения не изолируют команды терминала.

Неизвестные поля и нулевые значения ограничений безопасности отклоняются. Это позволяет обнаруживать опечатки вместо их молчаливого игнорирования.

## Запуск сервера

Передайте конфигурацию явно:

```console
fs-mcp-rs --config /absolute/path/to/fs-mcp-rs.toml
```

Или используйте переменную окружения:

```console
FS_MCP_CONFIG=/absolute/path/to/fs-mcp-rs.toml fs-mcp-rs
```

PowerShell:

```powershell
$env:FS_MCP_CONFIG = "C:\config\fs-mcp-rs.toml"
fs-mcp-rs
```

Проверьте работоспособность:

```console
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ:

```text
ok
```

MCP endpoint:

```text
http://127.0.0.1:8000/mcp
```

## Публикация сервера через безопасный туннель

Для тестирования с удаленным MCP-клиентом оставьте `fs-mcp-rs` привязанным к loopback-интерфейсу и опубликуйте его через туннель. Сначала запустите сервер:

```console
fs-mcp-rs --config ./fs-mcp-rs.toml
```

Перед созданием туннеля проверьте локальный endpoint:

```console
curl http://127.0.0.1:8000/health
```

> [!CAUTION]
> Публичный URL туннеля открывает удаленным клиентам путь к инструментам и корням файловой системы, разрешенным вашей конфигурацией. Начинайте с `read_only = true`, предоставляйте только узкие корни, не открывайте каталоги с секретами и останавливайте туннель после использования. Быстрые туннели предназначены для разработки, а не для постоянного production-хостинга.

### Cloudflare Tunnel

Установите [`cloudflared`](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/) и создайте временный Quick Tunnel:

```console
cloudflared tunnel --url http://127.0.0.1:8000
```

`cloudflared` выведет временный адрес наподобие `https://random-name.trycloudflare.com`. Добавьте к нему путь `/mcp`:

```text
https://random-name.trycloudflare.com/mcp
```

Для постоянного домена создайте именованный Cloudflare Tunnel, привяжите к нему DNS-имя и направьте его на `http://127.0.0.1:8000`. Долгоживущие развертывания следует защищать через Cloudflare Access или другой слой аутентификации.

### ngrok

Установите [`ngrok`](https://ngrok.com/download), при необходимости авторизуйте CLI и запустите HTTP-туннель:

```console
ngrok http 8000
```

Возьмите показанный ngrok HTTPS-адрес и добавьте `/mcp`:

```text
https://example.ngrok-free.app/mcp
```

Локальный интерфейс просмотра запросов обычно доступен по адресу `http://127.0.0.1:4040`. В нем могут отображаться детали запросов, поэтому оставляйте его локальным и не публикуйте наружу.

### Подключение удаленного MCP-клиента

Укажите публичный HTTPS-адрес как HTTP/Streamable HTTP MCP-сервер:

```json
{
  "mcpServers": {
    "filesystem": {
      "transport": "http",
      "url": "https://your-public-host.example/mcp"
    }
  }
}
```

После запуска туннеля проверьте оба endpoint:

```console
curl https://your-public-host.example/health
curl -i https://your-public-host.example/mcp
```

Ответ, отличный от `200`, на обычный `GET /mcp` может быть нормальным, поскольку MCP использует протокольные запросы. Главное, чтобы `/health` был доступен, а MCP-клиент мог инициализировать сессию.

### Production-хостинг

Для постоянного развертывания предпочтительнее приватная сеть/VPN или именованный туннель с аутентификацией. Запускайте `fs-mcp-rs` от отдельной низкопривилегированной учетной записи через менеджер сервисов, оставляйте привязку к loopback, завершайте TLS на туннеле или reverse proxy, ограничивайте доступ клиентов, фиксируйте путь конфигурации и контролируйте логи. Не используйте незащищенный публичный URL как единственную границу безопасности.

## Настройка MCP-клиента

Запустите `fs-mcp-rs` как долгоживущий сервис, затем добавьте HTTP MCP-сервер в клиент, указав URL `/mcp`. Форматы конфигурации различаются между продуктами, поэтому точные имена полей смотрите в документации клиента.

Общий пример:

```json
{
  "mcpServers": {
    "filesystem": {
      "transport": "http",
      "url": "http://127.0.0.1:8000/mcp"
    }
  }
}
```

Не публикуйте endpoint в недоверенной сети. Сервер ограничивает область файловой системы, но не заменяет аутентификацию хоста, TLS, межсетевой экран или аутентифицированный reverse proxy.

## Доступные инструменты

- `list_directory`: список непосредственных дочерних элементов каталога.
- `read_file`: чтение диапазона байтов UTF-8 с явными смещением и длиной.
- `write_file`: атомарное создание или замена UTF-8-файла.
- `search_files`: поиск путей, имя файла которых содержит строку.
- `search_content`: регистронезависимый литеральный поиск или поиск по регулярному выражению в текстовых файлах.
- `get_capabilities`: безопасный отчет об эффективных ограничениях, корнях, версиях протокола и доступных инструментах.
- `list_tree`: ограниченное, детерминированное и постраничное плоское дерево каталогов.
- `apply_patch`: атомарное применение проверенного unified diff для одного файла; `dryRun` ничего не изменяет.
- `file_info`: подробные метаданные и опциональный потоковый BLAKE3-хеш.
- `create_directory`: создание одного каталога; родительские каталоги должны существовать.
- `remove`: удаление одного файла или пустого каталога.
- `hash_file`: вычисление BLAKE3-хеша файла.
- `move`: перемещение без перезаписи существующего назначения.
- `edit_text`: атомарная замена точно указанного числа текстовых совпадений.
- `terminal_start`: запуск постоянной команды с немедленным возвратом идентификатора сессии.
- `terminal_read`: инкрементальное чтение событий stdout/stderr по байтовому курсору с опциональным long polling.
- `terminal_write`: запись UTF-8-данных в stdin работающей сессии.
- `terminal_close_stdin`: отправка EOF работающей сессии.
- `terminal_kill`: завершение всего дерева процессов сессии.
- `terminal_close`: явное удаление завершенной сессии и сохраненного вывода.
- `run_command`: выполнение произвольной shell-команды с рабочим каталогом и тайм-аутом с ожиданием завершения для обратной совместимости.

Изменяющие инструменты остаются видимыми в режиме только для чтения, но возвращают понятную ошибку. Благодаря этому одна конфигурация клиента подходит для read-only и writable развертываний.

## Модель безопасности

1. Каждый читаемый путь канонизируется и проверяется на принадлежность настроенным корням.
2. Каждая цель записи проверяется через существующий родительский каталог.
3. Переход по символическим ссылкам по умолчанию запрещен.
4. Чтение, запись, число результатов и параллелизм ограничены.
5. Для записи сначала используется временный файл в целевом каталоге.
6. `edit_text` требует ожидаемое число замен, предотвращая случайные массовые изменения.

Рекомендуемая конфигурация для production:

- Начинайте с `read_only = true`.
- Предоставляйте минимально необходимые корни; не открывайте весь домашний каталог или диск без конкретной причины.
- Привязывайтесь к loopback-интерфейсу.
- Запускайте сервер от отдельной низкопривилегированной учетной записи ОС.
- Не включайте скрытые файлы без необходимости.
- Для удаленного доступа используйте аутентификацию и TLS перед сервером.
- Создавайте резервные копии доступных для записи корней и проверяйте процедуру восстановления.

На проверки файловой системы могут влиять гонки ОС, если другой процесс способен заменять компоненты пути во время операции. Не делите доступные для записи корни с недоверенными локальными пользователями.

## Примеры новых инструментов

Получение действующих ограничений без пробных обращений к путям:

```json
{"name":"get_capabilities","arguments":{}}
```

Получение страницы детерминированного дерева с продолжением по возвращенному курсору:

```json
{"name":"list_tree","arguments":{"path":".","depth":2,"include":["**/*.rs"],"exclude":["target/**"],"maxEntries":100,"cursor":null}}
```

Проверка патча одного файла без изменения цели:

```json
{"name":"apply_patch","arguments":{"path":"README.md","patch":"--- a/README.md\n+++ b/README.md\n@@ -1 +1 @@\n-old\n+new\n","expectedBlake3":null,"dryRun":true}}
```

Получение подробных метаданных и потокового хеша:

```json
{"name":"file_info","arguments":{"path":"README.md","includeHash":true}}
```

`apply_patch` отклоняет бинарные, многофайловые патчи, а также создание, удаление и переименование. Все блоки применяются атомарно или не применяются совсем. Сохраняются исходные окончания строк LF/CRLF и наличие финального перевода строки. `dryRun` выполняет полную проверку, но никогда не записывает данные, включая режим только для чтения.

## Ограничения дерева и патчей

Следующие необязательные поля `[filesystem]` имеют проверенные значения по умолчанию, поэтому существующие конфигурации продолжают работать:

| Поле | По умолчанию | Ограничение |
|---|---:|---|
| `tree_max_depth` | `8` | Положительная максимальная глубина рекурсии |
| `tree_max_entries` | `1000` | Положительное максимальное число элементов на странице |
| `tree_max_warnings` | `32` | Положительное максимальное число предупреждений о пропущенных элементах |
| `patch_max_bytes` | `1048576` | Положительный максимальный размер unified diff в байтах |
| `patch_preview_bytes` | `16384` | Положительное значение не больше `patch_max_bytes` |

`list_tree` использует настройки поиска для скрытых файлов и Git ignore. Курсоры непрозрачны и привязаны к каноническому корню, глубине и фильтрам. Каждый запрошенный путь по-прежнему проходит через `Policy`; эти инструменты не ослабляют изоляцию корней, read-only режим или ограничения символических ссылок.

## Переход со `stat`

`file_info` заменяет прежний публичный инструмент `stat`. `stat` больше не публикуется и не обрабатывается. Клиентам следует перейти на `file_info`; включайте `includeHash` только при необходимости BLAKE3-хеша.

## Логирование

Управляйте структурированными логами через `RUST_LOG`:

```console
RUST_LOG=info fs-mcp-rs --config ./fs-mcp-rs.toml
```

Используйте `debug` только для диагностики, поскольку пути могут попадать в отладочный вывод.

## Разработка и проверка релиза

Перед подготовкой релиза выполните полный набор локальных проверок:

```console
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo publish --dry-run -p fs-mcp-rs
```

В Windows `scripts\build.cmd` выполняет те же проверки. Настоящий релиз на crates.io также должен пройти CI в Windows, Linux и macOS и быть протестирован как минимум с одним реальным MCP-клиентом.

Методология бенчмарков описана в `BENCHMARKS.md`. Заявления о производительности должны сопровождаться исходными результатами, характеристиками машины, конфигурацией и хешами коммитов.
